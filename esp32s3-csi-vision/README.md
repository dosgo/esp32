# ESP32-S3 · Wi-Fi CSI 感知成像

不用摄像头，用 Wi-Fi 信号本身「看」东西。

ESP32-S3 在接收每一个 Wi-Fi 帧时，物理层前导码里就带着 **CSI（Channel State Information，信道状态信息）**——
64 个 OFDM 子载波上的复数增益（I/Q）。人在链路附近走动，多径被扰动，这些子载波的幅度就会跟着抖。
把 64 路子载波按时间铺成瀑布图，就得到一张「射频成像」图：

- **没人 / 完全静止** → 平滑的横向条纹，几乎不动
- **有人坐着呼吸** → 细密的轻微波纹
- **有人走动** → 明显的横向扰动带扫过

页面地址：`http://<ESP32的IP>/`（串口会打印）

---

## 先看效果（不用板子）

双击 `preview.html`，用浏览器打开。里面的数据是本地模拟的，

真机跑起来之后，打开 `http://<IP>/` 看到的就是同一套界面。

## 硬件

| 项目 | 要求 |
|---|---|
| 芯片 | ESP32-S3（**必须 S3 / C3 / C6 这类支持 CSI 的**，经典 ESP32 也可以） |
| 模组 | N16R8 或类似，本项目实测目标为 16MB flash + 8MB PSRAM（PSRAM 未使用） |
| 天线 | 板载即可，但**外置天线效果明显更好**（CSI 对信噪比敏感） |
| 路由器 | **必须 2.4GHz**，ESP32-S3 不支持 5GHz |
| 接线 | 只要一根 USB 线，不需要任何外设 |

## 三步跑起来

### 1. 烧写

```bash
cd D://esp32//esp32s3-csi-vision
cargo run --release
```

（`espflash` 会自己找串口并进 monitor。没装的话先 `cargo install espflash`。）

### 2. 配网（网页填，不用改代码）

手机连热点 **`CSI-Vision`** / 密码 **`csi12345`**，打开 `http://192.168.4.1/setup`，
填 Wi-Fi 名和密码，点「保存并连接」。设备会写 flash 并自动重启去连。

配过的 Wi-Fi 会记住，以后开机自动连。换网络随时回来改。

### 3. 打开页面

配网成功后，主页顶栏的「网络」标签会变成绿色并显示 IP，
也可以直接在串口日志里看：

```
[csi]   98 帧/秒 | rssi  -47 | 56 路子载波 | 53 ℃ | IP 192.168.1.23
```

浏览器（手机 / 电脑都行，只要和 ESP32 在同一个 Wi-Fi 下）打开 `http://192.168.1.23/`。

> **不配网也能用**：连热点后直接打开 `http://192.168.4.1/` 就有画面。
> AP 模式同样采 CSI —— 浏览器每 10ms 的 WebSocket 心跳本身就是下行帧。
> 区别是 AP 模式全靠浏览器喂数据，页面一关就停了；STA 模式还有固件 ping 网关打底。

### 为什么两个页面「看起来不一样」

两个 stack 返回的是**同一份 `index.html`**，HTML 一个字节都不差。观感差异只来自数据：

| | STA 侧（局域网 IP） | AP 侧（192.168.4.1） |
|---|---|---|
| CSI 触发源 | 固件 ping 网关 **100Hz** + 浏览器心跳 | 只有浏览器心跳 |
| 实测帧率 | **60 ~ 150 fps** | 25 ~ 40 fps，随信号抖动 |
| 瀑布图观感 | 条纹连续，动作扰动清晰 | 数据稀疏，像「不太动」 |

根因：`ping_task` 依赖 `stack.config_v4().gateway`，**AP 侧没有网关，ping 任务直接跳过**。

现在页面底部会自己报模式：AP 模式显示黄色提示「热点直连模式 · 只有浏览器心跳在采数」，
STA 模式显示正常说明。顶栏网络标签在 AP 页面也会带上「路由器」前缀，
避免把它误认成当前访问地址。

## 怎么判断「成功了」

看串口那一行，三个数字都对就说明通了：

| 指标 | 正常值 | 不对说明什么 |
|---|---|---|
| `帧/秒` | **50 ~ 250** | 0 = CSI 没触发（或页面没打开）；个位数 = 省电模式没关 / 没 ping 通网关 |
| `rssi` | -30 ~ -70 dBm | -90 以下太弱，换个位置，或离路由器近一点 |
| `子载波` | **64**（S3 实测） | 0 = 回调没被调用过 |

页面上的表现：

- **瀑布图有条纹在滚** → CSI 通了
- **一直纯黑 + 中间那行字** → 没收到数据，回到串口看帧率
- **有条纹但纹丝不动** → 通了，只是房间里真的没人动（用手在板子和路由器之间挥一下试试）

## 页面怎么读

| 区域 | 含义 |
|---|---|
| **时频瀑布图** | 横轴 = 64 个子载波（频率），纵轴 = 时间（往下滚），亮度 = 信号强度。最核心的视图 |
| **子载波响应** | 当前这一帧 64 路子载波的实时幅度 |
| **运动能量** | 相邻帧之间「波形形状」变化的平均绝对值。跟绝对信号强度无关，只反映扰动 |
| **子载波活动强度** | 最近一小段时间里，哪几路子载波被扰动得最凶（即哪些多径路径在变） |
| **灵敏度滑块** | 判定阈值缩放。环境噪声大就调低（更迟钝），想抓呼吸微动就调高 |
| **顶栏「芯片」** | ESP32-S3 片上温度传感器。超过 62℃ 变黄、75℃ 变红（只做趋势参考，见下） |
| **顶栏「网络」** | 绿色 = 已连路由器（显示 IP），黄色 = 未配网，点一下进配网页面 |

最有效的摆法：**ESP32 和路由器之间隔着一条人走的通道**。
人体主要成分是水，对 2.4GHz 吸收极强，穿过链路时 CSI 抖动会非常明显。

## 原理与设计取舍

### 触发流量：为什么最后用的是 DNS 查询

CSI 只在**收到帧**的时候上报。没有下行流量，`on_csi` 回调一次都不会触发，页面永远是空白。
所以必须有人持续给 ESP32 发包。这一条踩了四个方案才通：

| 方案 | 结果 |
|---|---|
| ping 网关（ICMP echo） | ❌ 本项目所在的 CPE **完全禁 ICMP**：发 702 个 ping，回包 0 |
| `dump_ack_en`（让 ACK 帧也上报 CSI） | ❌ 这版 esp-radio 驱动不上报 ACK 的 CSI |
| 让 ESP32 连自己的局域网 IP（数据绕路由器一圈回来） | ❌ 路由器开了**客户端隔离**，自己发给自己收不到 |
| UDP 广播 | ❌ 射频不会把自己发出的帧回环到自己的接收路径 |
| **向网关发 DNS 查询** | ✅ **响应率 98%**，CSI 稳定 100 fps |

**DNS 为什么一定通**，两个原因：

1. **DNS 是刚性需求**：路由器可以禁 ICMP、可以隔离客户端，但**不能不应答 DNS**，
   否则整个网络没法上网。而 DHCP 已经把网关同时设为 DNS 服务器，地址现成。
2. **路径是「客户端 → 网关」**：客户端隔离只拦客户端**之间**的单播，
   到网关的基础转发不受影响。

实现上完全不解析响应内容——只要响应包回来，射频就收到了一帧带完整前导码的数据帧，
CSI 自然上报。22 字节的查询包，50Hz 也就 1.1KB/s。

配置在 `config::DNS_INTERVAL_MS`（默认 20ms = 50Hz）。
实测 10ms 能把 CSI 顶到 254 fps，但 50Hz 已经远超分析所需（50fps 就够），
而且每秒问路由器 50 次比较友好。

> 调度用的是**绝对节拍**而不是固定 sleep：`send` + 等响应本身要 1~4ms，
> 固定 sleep 会让实际周期漂到 22~24ms。改成累加目标时刻、落后才补齐后，
> 实测稳定在 50 Hz（之前是 72~90Hz 乱飘）。

### 为什么只保留振幅、丢掉相位

相位要做载波频偏（CFO）和采样频偏（SFO）校准。不校准的话相位**每个包都在随机跳**，
看起来全是噪声，根本没法用。ESP32 没有暴露参考相位，做校准要额外的收发对和算法。
振幅抖动的物理意义已经足够做人体存在 / 动作识别了。

### 为什么 WebSocket 不用 `select` 同时收和推

`ws_read` 内部是多次 `read` 拼出来的，一旦被 `select` 取消（CSI 每 20ms 就绪一次，几乎必然先到），
已经读进缓冲的半个帧头就丢了，**之后整条流的帧边界全部错位**，页面会一直解析失败。

所以反过来设计：由浏览器的 10ms 心跳驱动循环，每读完一帧就顺手把最新 CSI 推出去。

### 为什么用 `Watch` 而不是队列

CSI 回调有 100~300Hz。用队列把每帧都推给浏览器，WebSocket 会被打满，而人眼 50fps 以上没差别。
`Watch` 只保留最新一帧，浏览器慢了就自然跳帧，永远不会积压出延迟。

## 局限（重要，别抱错期待）

**这不是光学成像。** 单条 Wi-Fi 链路只有「一路发射 → 一路接收」，物理上测不出目标的方位和形状。
你能得到的是：

✅ 有人在不在场
✅ 有没有动、动得多剧烈
✅ 动作的大致节奏（走路 / 挥手 / 呼吸）
✅ 扰动发生在哪些多径路径上

❌ 人的轮廓、姿态、位置坐标

想要真正的「穿墙成像」，需要多发多收（MIMO 阵列）+ 逆散射算法，那是科研级设备的事。
ESP32-S3 单天线只能做**感知**，做不了**成像**。本项目的「成像」指的是
把 64 路信道响应铺成可视化的时频图，这个说法在 CSI 领域是通用的。

## 调参

全在 `src/config.rs`：

| 参数 | 默认 | 说明 |
|---|---|---|
| `PING_INTERVAL_MS` | 10 | ping 间隔。想更细可到 5，但很多家用路由会开始丢 ICMP；低于 4ms 反而更慢 |
| `PUSH_MS` | 20 | 推给浏览器的帧间隔（50fps） |
| `DNS_INTERVAL_MS` | 20 | DNS 触发查询间隔。50Hz → CSI 约 100fps；改 10ms → 约 250fps |
| `WEB_SESSIONS` | 2 | 同时支持几个网页连接 |

## 关于芯片温度

ESP32-S3 的片上温度传感器**没有烧出厂校准值**，所以绝对值会有 ±5℃ 左右的偏差，
而且读数更接近**芯片结温**而不是环境温度 —— 持续跑 Wi-Fi AP 时比室温高 20℃ 很正常。

所以它适合看**趋势**：烫不烫、加外壳后升多少、夏天会到多少。
想当环境温度计用是不行的。

（esp-hal 1.1.2 的 `tsens` 模块只对 C2/C3/C6/H2 编译，S3 上得直接写
`SENS.SAR_TSENS_CTRL` 寄存器，`soc_temp.rs` 里就是这段。）

## 调试与验证工具

`tools/` 下三个脚本，都是排查这一路问题留下来的，后面改代码能用上。

### `serial_log.py` —— 抓完整启动日志

```bash
python tools/serial_log.py COM3 10
```

`espflash monitor` 是连上之后才开始收，会丢掉最关键的 WiFi / CSI 初始化那几百毫秒
（恰好是最常出问题的地方）。这个脚本先占住串口、再拉 RTS 复位，从 ROM 第一条日志就能收到。

> 注意：直接用 `serial.Serial()` 读串口会读不到任何东西 —— pyserial 默认拉高 RTS，
> 等于把板子按在复位态。必须 `dtr=False; rts=False`。

### `check_page.js` —— 用真实 CSI 数据回归页面逻辑

```bash
node tools/check_page.js
```

不依赖浏览器，在模拟 DOM 里跑一遍 `index.html` 的真实绘图代码，喂的是
`.data/csi_sample.json`（从板子上抓的 320 帧真实数据），验证：

- 页面 JS 初始化不抛异常
- CSI 二进制帧解析正确（rssi / n / amp / ts）
- 归一化 → 运动检测 → DOM 更新整条链路正常
- **静止和运动的判定能拉开距离**（实测静止 0.11 → 叠加扰动 0.46）
- 温度 / 网络标签更新路径正常

改完前端先跑这个，比开浏览器手点快得多。脚本最后会做一次「叠加人为扰动」的对比，
如果哪天改了归一化或阈值导致区分度不够，它会直接报出来。

## 踩过的坑（改动时注意）

按「最容易再次踩到」排序，每条都是实测撞出来的。

### 1. `Watch<M, T, N>` 的 `N` 是**订阅者数量上限**，不是缓冲深度

这条最坑。写成 `Watch<_, _, 1>` 表示**整个系统同时只允许一个 receiver**，
第二个 WebSocket 会话调用 `receiver()` 会返回 `None`。

现象：第一个页面异常断开后 receiver 没释放，之后**任何**新连接都会走到
`.unwrap()` 处 panic，固件直接停摆 —— 看起来就像「板子死了、网页打不开」。

正确写法：`Watch<_, _, 8>`（远大于 `WEB_SESSIONS`），并且拿到 `None` 时优雅退出，
绝对不要 `unwrap()`。一个页面出问题不该把整个固件打崩。

### 2. smoltcp 的 socket 池要把「所有」socket 都算进去

每个 `StackResources<N>` 的 N 是总槽位。STA 侧的账：

```
WEB_SESSIONS(5) 个监听 TCP
+ 1 个 ICMP（ping 任务）
+ 1 个 DHCP 客户端
= 7
```

之前写 6，在 `WEB_SESSIONS=3` 时刚好塞得下（3+1+1=5），加到 5 就溢出 →
`panicked at smoltcp/socket_set.rs: adding a socket to a full SocketSet`。
现在给 10，留 3 个余量。

### 3. AP 必须显式设发射功率，否则连扫都扫不到

`AccessPointConfig` 不设 `set_max_tx_power()` 时用的是芯片默认档，
实测**电脑和手机都扫描不到这个热点**（信号 0%）。

```rust
controller.set_max_tx_power(80)?;   // 80 = 20dBm，设完立刻 97%
```

设置前后差别是「完全找不到」和「信号 97%」，不是渐变。

### 4. 客户端系统会自动切回「有外网」的 WiFi

AP 模式最大的敌人不是固件，是手机/电脑的系统策略：

- Windows 连上无外网的热点后，会自动切回有网的路由器
- 安卓/iOS 会提示「无法访问互联网」，部分机型直接切回移动数据

**这时候板子一切正常，客户端已经不在这个网里了** —— 表现同样是「网页打不开」。

所以调试时别在 AP 模式上恋战，**配网进 STA 模式**才是稳定形态。
真要在 AP 模式下测，得先关掉手机移动数据、或让系统忘记原来的路由器。

### 5. `close()` 之后立刻 `abort()` 会发 RST，浏览器白屏

`close()` 只是进入 FIN-WAIT，数据靠 `flush()` 发出去。flush 完立刻 abort 会发 RST，
对端正收着 20KB 页面就报「连接被重置」。

正确顺序：`close()` → `flush()` → 等 120ms → `abort()`。

### 6. `accept()` 失败后别久等

那个 socket 在非监听状态时新连接直接 RST。等 50ms 就够，等 500ms 会让
「网页偶发打不开」变成「经常打不开」。

### 7. smoltcp 默认不回复 ICMP echo（所以 ping 不通是正常的）

没开 `auto-icmp-echo-reply` feature 时，ping ESP32 一定超时。
**不能用 ping 判断设备死活**，用 TCP 连 80 端口或者看串口日志。
ARP 表里有它的 MAC 就说明二层是通的。

### 8. `esp-radio` 的 `csi` feature 依赖 `unstable`

两个必须同时开，否则 `set_csi` 根本不存在。

### 9. CSI 回调运行在 Wi-Fi 任务上下文

不能 `.await`、不能长时间持锁、不能分配内存。只做纯计算 + 一次 `Watch` 写入。

### 10. 省电模式必须关

`PowerSaveMode::Minimum/Maximum` 会让射频按 DTIM 休眠，收包节奏稀疏且不均匀，
CSI 帧率掉到个位数。用 `None`。

### 11. `esp-hal` 必须锁 `=1.1.2`

`esp-radio 0.18` / `esp-rtos 0.3` 只认 1.1.x，不锁会解出 1.2 然后类型打架。

### 12. `Interface` 来自 `esp_radio::wifi`，不是 `embassy_net`

后者的是 private（E0603）。

### 13. 编译前把 Xtensa 工具链加进 PATH

```bash
export PATH="$HOME/.cargo/bin:$HOME/.rustup/toolchains/esp/xtensa-esp-elf/bin:$PATH"
```

否则报 `linker xtensa-esp32s3-elf-gcc not found`。

### 14. pyserial 打开串口默认拉高 RTS，会把板子按在复位态

裸用 `serial.Serial('COM3', 115200)` 读不到任何输出，因为 RTS=1 等于按住复位。
必须：

```python
s = serial.Serial('COM3', 115200)
s.dtr = False
s.rts = False
```

`tools/serial_log.py` 里做了完整的复位序列，能从 ROM 第一条日志开始收。
